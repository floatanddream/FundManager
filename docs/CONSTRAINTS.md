## 一、技术栈（已确认，不可擅自更改）

```
monorepo      pnpm workspace（apps/*, packages/*）
语言          TypeScript（strict）
运行时        Node 24 —— 原生执行 .ts、原生 fetch、原生 node:sqlite
后端          Fastify + Service / Repository 分层
数据库        node:sqlite（Node 内置）+ Drizzle ORM
校验          Zod（共享契约放 packages/shared）
前端          React 19 + Vite + shadcn/ui + Tailwind
图表          ECharts（手写 React wrapper）
数据请求      TanStack Query
测试          Vitest
定时任务      CLI + Windows 计划任务（非常驻进程）
通知          node-notifier（桌面通知）
缓存          SQLite 表
```

### 已实测的硬事实（2026-11-17，本机 Node v24.21.0）

| 事实 | 影响 |
|---|---|
| Node 原生执行 `.ts` ✅ | 不需要 tsx |
| Node **执行不了装饰器** ❌ `SyntaxError` | **不用 NestJS**（它全靠装饰器）|
| `node:sqlite` 可用 ✅ | **不用 `better-sqlite3`**（原生模块，Windows 需编译，Node 24 可能无预编译包）|
| Node 自带 `fetch` ✅ | 不需要 axios |
| `registry.npmjs.org` 可达 ✅ | 可正常装包 |
| **相对导入必须带 `.ts` 后缀** | 用 `.js` 后缀指向 `.ts` 文件会 `ERR_MODULE_NOT_FOUND`（实测）。与 TypeScript 官方推荐的 `.js` 约定**相反**，因为本项目无构建步骤、由 Node 直接执行 |
| **Drizzle 不支持 `node:sqlite`** | 需用 `drizzle-orm/sqlite-proxy` 自建约 15 行适配器（已实测跑通）|

### 明确不用

| 不用 | 理由 |
|---|---|
| Redis | 部署形态是**各自部署**（见 §7），每个实例仍是单进程单用户，跨进程缓存/会话/分布式限流/任务队列一个都不存在。Windows 无官方版，需 WSL/Docker。**接口留着（`CacheStore`），实现不写** |
| NestJS | 复杂度在 `core` 与 `datasource`，`apps/server` 很薄，框架的结构价值无处施展。且需额外构建步骤 |
| Prisma | 需 codegen + 引擎二进制，过重 |
| Turborepo | 项目规模用不上 |
| Redux | 读数据看板，TanStack Query 足够 |
| `better-sqlite3` / `tsx` / `axios` | 见上表，Node 24 已内置替代 |

### 预留的扩展缝（三条，均为「一个接口 + 一处装配」）

| 会变的 | 接口 | 现在 | 将来 |
|---|---|---|---|
| 缓存 | `CacheStore` | SQLite 表 | Redis |
| 数据库 | Drizzle | node:sqlite | Postgres |
| 数据源 | `FundDataSource` | 天天基金 / 腾讯 | 换源 |

换实现时**业务代码零改动**。装配点全局只有一处。

## 二、分层规矩

```
Route (Fastify)    只做 HTTP：校验入参、调 Service、返回
   ↓
Service            编排：取数 → 算 → 存 → 通知。不含算式
   ↓
   ├── Repository   本地 SQLite 持久化（可靠，不会挂）
   ├── DataSource   外部数据获取（会挂，需重试/缓存/降级）
   └── core         纯计算，无 IO
```

**规矩 1：Service 不算数，core 才算数。**
Service 只搬运数据。任何计算都调用 `core`。理由：`core` 是纯函数，测试不需要 mock 数据库和网络——而算错了亏的是钱。

**规矩 2：Repository 与 DataSource 不合并。**
两者失败模式不同：本地库可靠，外部接口会挂。混在一起，缓存与降级语义无法表达。

**规矩 3：`packages/core` 不 import 任何框架、不 import 任何 IO。**
它是纯函数库。这条保证了后端框架选择可逆（换框架只改壳）。

## 四、必须遵守的硬规则

### 1. 三种价格在类型上隔离

```ts
type NavConfirmed = { kind: 'nav'      ; value: number; date: string }  // T-1 确认净值
type NavEstimate  = { kind: 'estimate' ; value: number; asOf: string; basis: string } // 盘中估算
type MarketPrice  = { kind: 'price'    ; value: number; asOf: string }  // 场内成交价
```

**收益与风险计算只接受 `NavConfirmed`。** 靠编译器拦住，不靠自觉。

### 2. 不下单

不碰任何交易接口，不存储平台凭证，不模拟客户端操作。系统只出主意。

理由：资金自动化容错率为零。

### 3. 不预测涨跌

不得输出「某基金将上涨/下跌」，界面文案也不得暗示预测能力。允许且仅允许：描述当前风险、蒙特卡洛概率区间（给分布不给点位）、历史情景压力测试。

### 4. 估算可以算，但必须标注方法与误差

> **2026-11-18 修订。** 原先此条写的是「主动基金一律不估值，写死」，**已推翻**。
> 推翻理由：把「算不准」当成了「不该算」，这是两回事。实测证明可以算，且误差可控——
> 只是必须把方法和误差摊开，而不是藏起来。

实测（`000001 华夏成长混合`，2026-11-17 单日，本机实测非推算）：

| 算法 | 覆盖净值 | 隐含涨跌 | 误差 | 相对误差 |
|---|---|---|---|---|
| 只用最新季报前十大 | 39.93% | +1.108% | -0.368pp | 50% |
| 只用半年报全量持仓 | 74.81% | +0.984% | -0.244pp | 33% |
| **拼接：新前十权重 + 旧全量尾部** | **64.92%** | **+0.879%** | **-0.139pp** | **19%** |
| 基金实际 | — | +0.74% | — | — |

拼接法 = 最新季报的前十大**权重**（1.5 个月前）+ 半年报的完整持仓**名单**（4.5 个月前），
尾部按股票仓位额度等比缩放。误差比只用前十大砍掉一半以上。

**规则：**

- **可以估算。** 被动基金（有跟踪标的）与主动基金都能算
- **每条估算必须携带三项**：所用持仓的报告期、覆盖比例、算法名。缺一不可
- **`NavEstimate` 的类型隔离是这件事成立的前提**——估算可以展示、可以比较，但**进不了收益与风险计算**。正因为它脏不到账上，才敢放开让用户看
- **误差分布未经统计验证。** 上表是「一只基金、一天」的观测，**不构成精度结论**。验收标准由计划 5 的统计验证确定（多基金 × 多交易日，尤其是经理调仓剧烈的时期），不得凭上表拍板
- 无跟踪标的的基金 → **不产出行业归因**（归因需要基准指数），界面显式标注「无基准」。但**估值不受此限**

### 5. 有效暴露取自业绩比较基准，不是「股票仓位」

实测 `011609`：股票仓位字段 = **0.41%**（联接基金，买的是 ETF），业绩比较基准给出 = **95%**。
字面代入前者会得出荒谬结果。

### 必须记住的口径限制

- **最新持仓只有前十大**（季报），**完整持仓只在半年报与年报**。两者都已滞后：季报约 1.5～4.5 个月，半年报/年报约 4.5～11 个月。因此重叠度、行业暴露、估值全部建立在**不完整且陈旧**的数据上——界面必须**同时**标注口径与数据时点，缺一即误导
- **场外基金没有实时净值**。净值由基金公司收盘后计算公布（约 19:00–23:00）。「此刻净值」不存在
- **联接基金要穿透**（名称含「联接」的，买的是对应 ETF）
- **分红/份额折算无自动来源** → 手工录入 + 事件提示（提示不等于自动记账，必须用户确认）
- **份额折算必须支持**：实测 `510300` 历史含「拆分：每份基金份额折算」，用户无操作份额也会变

## 六、账务规矩

- **数据挂在「账本」下，不是挂在「用户」下**。见 §7.2，这条要现在做，后补很痛
- **账本存流水，不存持仓状态**。持仓由流水推导
- **必须支持 `split`（份额折算）**，否则账永远对不平
- **现金分红与红利再投是两种事件**，分开记（前者份额不变、现金离开；后者份额增加）
- **一致性检查，不做自动修正**：用「上期份额 + 本期流水」推算应有份额，与用户录入比对。不一致就拦住并要求确认，**绝不悄悄改账**
- **成本价可缺**：查不到成本价的基金仅做风险跟踪，不显示个人盈亏，界面标注原因
- **收益两个数分开放**：资金加权（XIRR，这笔钱赚多少）与时间加权（TWR，经理行不行）。App 里的「持仓收益率」两个都不是

## 七、部署与开源

本项目**开源**，部署形态为**各自部署**（self-host）：使用者各自 fork、各自在本机跑一份，数据各自留在本地。**不做中心服务器，不提供多用户共用的托管实例。**

### 7.1 由此产生的硬要求

| 要求 | 说明 |
|---|---|
| **免责声明** | 金融工具，必须有「不构成投资建议」。已在 `README.md` |
| **数据来源说明** | 抓取的是非官方公开接口，须说明来源与无关联性 |
| **不得硬编码本机信息** | 不出现 `C:\Users\07\...` 之类的路径，不出现特定持有人的数据 |
| **配置化** | 阈值、通知方式、数据源选择都要可配，不能写死作者偏好 |
| **首次运行要能跑通** | 别人 clone 下来得能装能跑。需要示例配置与清晰报错 |
| **错误信息要能自解释** | 作者调试过的坑，使用者没有那段经验 |

### 7.2 账本概念（现在就要做，且不能后补）

**数据挂在「账本」下，不是挂在「用户」下。**

- 现在只有 1 个账本（自己），将来可以是 N 个
- 好处：**对自用立刻有价值**（分「实盘」「模拟」，或给家人单独记一本），且将来若真要加多用户，是**加一层**（账本挂到用户下），不是**改一层**
- **这是唯一一个「后补很痛」的设计决定**：往所有表加字段并回填数据，比一开始设计好贵得多。其余都能后补

### 7.3 绝不提交个人数据

`README` 公开意味着仓库可能被任何人看到。**个人持仓、成本价、账户信息绝不可进入版本库。**

- `.gitignore` 已屏蔽 `data/`、`*.db`、`.env`、本地配置
- 文档与示例中**只能用公开基金代码**（如 `011609`），不得出现真实持仓组合
- 提交前自查

## 八、代码风格

### 8.1 数值（已定，不可协商）

- 金额、净值、份额一律用 `number`，**不引 decimal 库**。实测浮点误差在小数点后 10 位（1000 笔累加得 `411522.6000000074`），而金额只到 2 位小数，引库是过度设计
- **比较一律用容差，禁止 `===`**，账本对账也不例外：

```ts
export function approxEqual(a: number, b: number, eps = 1e-9): boolean
```

- 佐证：`0.1 + 0.2 !== 0.3`

### 8.2 日期（已定，不可协商）

- 业务代码**只许 `YYYY-MM-DD` 字符串**
- **禁止带时间的日期字符串进入业务逻辑。** 实测陷阱：

  ```
  Date.parse('2024-01-01')         → 2024-01-01T00:00:00Z   按 UTC 解释
  Date.parse('2024-01-01T00:00:00') → 2023-12-31T16:00:00Z   按本地解释
  ```

  同一天相差 8 小时，会让日期**静默错位一天**，跨年的收益可能被算到上一年
- 日期运算集中在工具函数内，**不让 `Date.parse` 散落各处**
- 盘中估值的时间戳（`asOf`）是独立类型，不与业务日期混用

### 8.3 错误分类（已定，不可协商）

| 情况 | 处理 | 例子 |
|---|---|---|
| **数学上无解** | 返回 `null` | 只买没卖，XIRR 不存在 |
| **参数非法** | **抛异常** | 传 `'2024/01/01'`、净值 `-1`、份额为负 |
| **数据缺失** | 返回 `null`，由调用方决定如何呈现 | 归一后现金流不足两笔 |

原则：`null` 表示「这个问题的答案不存在」，抛异常表示「调用方写错了」。前者是正常业务，后者是 bug，必须早暴露而不是让 `NaN` 静默往下传。

### 8.4 包出口（已定）

**显式列名导出，不用 `export *`**：

```ts
// packages/shared/src/index.ts
export { approxEqual } from './number.ts'
export { navConfirmed, navEstimate, marketPrice, isConfirmed } from './price.ts'
export type { AnyPrice, MarketPrice, NavConfirmed, NavEstimate } from './price.ts'
```

理由：`index.ts` 是两个包之间的公共边界。`export *` 会让边界糊掉，什么都从任何文件溜出去，还容易埋循环依赖。

### 8.5 class 的使用（已定）

- `packages/core` 与各解析逻辑：**一律纯函数**
- 只有**必须持有状态**的（数据库连接、HTTP 客户端）才用 class，且**仅出现在 `apps/server` 层**

### 8.6 格式化（已定）

**oxlint（管 lint）+ Prettier（管格式）**。web 模板自带的 oxlint 保留不动。

### 8.7 注释规范（已定）

**三类，按函数的位置和复杂度分：**

| 位置 | 写法 |
|---|---|
| **导出的公共函数** | **JSDoc**（`/** */`）。参数/返回值语义不显然时用 `@param` / `@returns`。**会抛异常的函数必须写 `@throws`**，并说明什么情况下抛——调用方要据此决定是否捕获 |
| **非导出的小函数** | 单行注释（`/** 一句说清做什么 */`） |
| **函数体内的复杂流程** | **必须写行内注释**。数值迭代、边界处理、公式推导，逐段说明 |

**判断"复杂"的标准：** 一个不了解这块业务的人，看代码能不能直接读懂。读不懂就要注释。

**铁律：注释解释「为什么」，不复述「做什么」。** 做什么代码已经说了。例如：

```ts
// ✗ 复述代码，零信息
// 取第一个元素
const first = flows[0]

// ✓ 解释为什么，有信息
// 分母为 0 说明这一期没有本金，收益率无定义——不能返回 Infinity 蒙混过去
if (base <= 0) return null
```

**其它：**
- 标识符用英文，注释与用户可见文案用中文
- **测试名用中文**。测试名是给人读的，读者是使用者

## 九、工程流程

### 9.1 git（已定）

**已初始化**，首次提交 `5621435`（2026-11-17）。

- **git 是审查能力的前提，不只是版本控制。** `superpowers:requesting-code-review` 靠 `BASE_SHA` / `HEAD_SHA` 划定审查范围——没有 git 就没有 SHA，那层独立审查直接失效
- **每个任务完成、测试全绿后提交一次**，提交边界与计划的任务边界一致
- **提交信息不得包含任何工具署名行**。`Co-Authored-By:` 指向 AI 工具、`Generated with ...`、`🤖 ...` 之类一律不加——提交信息只写改动本身（2026-11-18 使用者明确要求）

### 9.2 测试数据策略（已定）

外部接口会变（已有实例：天天基金盘中估值接口 404），因此测试分两层：

| 层 | 打不打真网络 | 数据来源 | 何时跑 |
|---|---|---|---|
| **单元测试** | 否 | 固定 fixture（真实响应存成文件） | 每次 |
| **契约测试** | 是 | 真实接口 | 定期；允许因接口变动而失败 |

- **分两层的意义**：接口挂了要被契约测试**发现**，但不能把日常测试**搞红**——测试一红就没人信，久了就没人看
- **fixture 走样是已知风险。** 每个 fixture 必须记录抓取日期与来源 URL，并提供重新抓取脚本
- 契约测试失败时的处置：先判断是接口真变了还是网络抖动，前者更新 fixture 并检查解析代码
