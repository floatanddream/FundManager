# 九、工程流程

### 9.1 git（已定）

**已初始化**，首次提交 `5621435`（2026-11-17）。

- **git 是审查能力的前提，不只是版本控制。** `superpowers:requesting-code-review` 靠 `BASE_SHA` / `HEAD_SHA` 划定审查范围——没有 git 就没有 SHA，那层独立审查直接失效
- **提交单位是功能，不是文件类型。** 每完成一个功能提交一次（不论功能大小），**代码 + 其文档 + 其测试合为一个提交**，类型用 `feat`
- **不要为文档单独开 `docs:` 提交。** 文档属于它服务的那个功能，跟着功能走。禁止「先 feat 代码、再 docs 补文档」这种成对提交
- **例外：规划与约束类文档不受上一条限制。** spec、plan、`docs/CONSTRAINTS/`、研究盘点这类文档**在任何代码之前**，没有可挂靠的功能提交，只能单独提交。（2026-11-18 补：原条款与仓库实际做法长期相抵触——计划 1/2/3 的每份文档都是单独提交的。**规矩应当描述实际做法，与实际长期不符的规矩只会被忽略。**）
- 提交边界与计划的任务边界一致
- **提交信息不得包含任何工具署名行**。`Co-Authored-By:` 指向 AI 工具、`Generated with ...`、`🤖 ...` 之类一律不加——提交信息只写改动本身（2026-11-18 使用者明确要求）

### 9.2 测试数据策略（已定）

外部接口会变（已有实例：天天基金盘中估值接口 404），因此测试分两层：

| 层 | 打不打真网络 | 数据来源 | 何时跑 |
|---|---|---|---|
| **单元测试** | 否 | 固定 fixture（真实响应存成文件） | 每次 |
| **契约测试** | 是 | 真实接口 | 定期；允许因接口变动而失败 |

- **分两层的意义**：接口挂了要被契约测试**发现**，但不能把日常测试**搞红**——测试一红就没人信，久了就没人看
- **fixture 走样是已知风险。** 每个 fixture 必须记录抓取日期与来源 URL，并提供重新抓取脚本
- 契约测试失败时的处置：先判断是接口真变了还是网络抖动，前者更新 fixture 并检查解析代码

### 9.3 运行形态（已定）

**前后端分开跑**（使用者选择，未采纳「Fastify 兼服务前端」的建议）。

- 后端 Fastify 一个进程；前端由独立静态服务提供
- 开发时前端走 Vite dev server，后端单独启动
- **由此产生三项待定，列入计划 5 / 6**：API 端口、前端如何得知 API 地址、CORS 配置

### 9.4 执行方式（已定）

**subagent 驱动，从简（2026-11-18 使用者改定）**：每个任务派一个全新 subagent 实现；
**不再逐任务派 reviewer**；整条计划跑完后**整体审查一次**。

- 理由：这是个人项目，逐任务审查的收益撑不起它的开销。质量主要由两样兜底——`core` 是
  纯函数（数进数出，手算可验）、三种价格类型在编译期隔离。
- 简报与报告仍然要写，但**只写要点**：简报给「要写什么 + 验收标准 + 边界」，报告给结论
  与验证输出。
- 依据 `superpowers:subagent-driven-development` 执行
- 审查依据 `superpowers:requesting-code-review`（需要 git SHA）

### 9.5 写法总原则：最简优先（已定，2026-11-18）

> 使用者原话：**「以后以最快，最方便，最直观，并且维护简单的方式去写。这是个个人 project」**，
> 紧接着补充：**「但是要保证代码质量、代码风格」**。

- **省结构**：少一层间接、少一个接口、少一个可配项。为「将来可能换实现」预留的缝，**只在真换起来痛时才值**。能用三个直白函数解决的就别造框架
- **直白优先于「正确但绕」**：能一遍看懂 > 抽象得漂亮
- **流程别叠层**：不搞「每任务审查 + 整体审查 + 修复波 + 复审」四层。**一次审查够了**，修完就收口
- **纠结点一到就停**：开始反复权衡时，多半已超出这条改动应得的投入。挑一个，写下去，错了再改

**但「简」指的是结构，不是做工——质量与风格不打折：**

| 该省（结构） | 不该省（做工） |
|---|---|
| 多余的层、接口、可配项、预留缝 | **命名**要准，不叫 `data`／`tmp` |
| 为「将来可能」做的抽象 | **注释**讲清「为什么」（§8.7） |
| 每任务一轮审查这类流程层数 | **错误分类**照 §8.3；该 `stale`／该抛／该拒的一个不能少 |
| 长篇的规划与设计文档 | **测试**少而准，不是少而糊（§8.8／§8.10） |
| 提交历史的反复重排 | **格式**：`pnpm format` 恒等、`pnpm typecheck` 干净 |

**一句话：代码可以短，但不能糙。** 砍掉一个抽象是省，砍掉一个 `@throws` 是欠债。
判断某次简化是否越界，问：这改的是**结构**还是**做工**？前者做，后者不做。
