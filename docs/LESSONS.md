## 计划 3：数据源层（`packages/datasource`）· 2026-11-18

11 个任务，20 个端点，105 个用例。一次整体审查 + 一轮修复 + 一次针对性复审。

### 1. 「实测结论」都是单样本，简报里必须明说别当它是事实

盘点和设计里**有 8 处**「实测结论」被实现期复核推翻：

| 原结论 | 实测 |
|---|---|
| `pingzhongdata` 的 epoch 毫秒按 UTC 解释 | 是**北京时间零点**，按 UTC 会整体早一天 |
| `jjcc` 的 `month` 参数被忽略 | 它决定**哪个报告期块返回全量** |
| 半年报/年报块不受 `topline` 限制 | 只有命中 `month` 的那个块是全量 |
| 表和表头的差异是「有空 `<td>`」 | 是**整列不存在**（9 列 vs 7 列） |
| 资产配置主备「等价」 | 主源只给 1 期、备源给 4 期 |
| `profile` 无备源 | `FundMNDetailInformation` **带**业绩比较基准 |
| `fqkline` 的 K 线键是 `day` | 指数是 `day`、个股/ETF 是 **`qfqday`** |
| 基金代码表 28,356 只 | 28,370 只 |

**根因**：这些结论大多是**一只基金、一个样本、一天**得出的。

**照做**：简报里写死一句「**别默认盘点是准的**，凡有疑问以真实响应为准，把发现写进报告」。每个端点任务都要真的去抓一次、复核一次。

### 2. 覆盖自审必须**逐项**对账，不能按节对账

计划 3 的自审写了「规格覆盖……**无缺口**」——但计划实际**漏掉了 `fundmobapi` 整族 4 个端点**，只覆盖 16/20，而设计承诺 20 个，且把这一族当作三条降级链的备源。

**根因**：自审只核对了「设计有哪几节 → 计划有哪几个任务」，没有逐个端点对。

**照做**：**条目类**计划（一堆端点/一堆字段/一堆规则）的自审，要**把设计承诺的每一项列出来，逐项指到具体任务**。清单式对账，不是目录式对账。

### 3. 数据源层的静默错值形态特别多，而且各不相同

计划 3 遇到的（每一条都会让用户看到**看着合理但错**的东西）：

- **软失败**：HTTP 200 + 错误码（缺 Referer → `ErrCode:-999`；UA 被拒 → `61136403` 且 `ErrMsg` 谎称「网络繁忙」）
- **解析失败伪装成空集合**：结构变了却返回 `[]`，用户看到「这只基金没有持仓」
- **无效代码静默降级**：`lsjz`/`qt`/`fqkline` 三处都是返回空、不报错
- **截断被当全量**：被 `topline` 截断的持仓当完整持仓
- **缓存键漏了维度**：键不含日期区间 → 先取窄区间、再取全量会拿到被截断的历史，且 `stale:false`、`loss:null`
- **字段装的是别的东西**：货币基金的 `Data_assetAllocation` 是份额流量，不是资产占比
- **fixture 被工具改写**：`eol=lf` 会改 CRLF 响应，manifest 的 `sha256` 就对不上了

**照做**：每接一个数据源，先问「**它失败时是什么样子**」，而不是「它成功时是什么样子」。失败形态是逐端点不同的，不能套模板。

### 4. 派发与环境上的坑

- **`Agent` 派发带 `model` 覆盖会挂死**（实测连续三次被拒/卡住），去掉该字段即通。**一律不写**
- **fixture 必须排除在 Prettier 之外**，并且 `.gitattributes` 要给 fixture 目录加 `-text` 禁掉行尾转换——否则 fixture 一入库哈希就变，`sha256` 全部失效
- **契约测试放在 `src/` 之外**（如 `test/contract/`），才天然落在 `vitest.config.ts` 的 include 之外，不用改现有配置就能与日常测试隔离
- **本机网络会拦域名**（`push2.eastmoney.com` 抓完一次后被 DNS 拦成 `127.255.0.1`）——拿不到真实样本的分支要如实标注，别假装验过

### 5. 从简的流程确实够用，但唯一那次审查要写厚

11 个任务只用了：**1 次整体审查 + 1 轮修复 + 1 次针对性复审**。够用。

**因为只有一次审查，所以要把它写厚**：

- 把**全部挂起项**列进去，要求**逐条分诊**（必须修 / 可延后 + 理由）
- 要它**实际核验**而不是表态——例如「提交署名行」要它跑 `git log --format=%B ... | grep -i`，不是问它「你觉得有没有」
- 点名要它盯**最容易静默出错的那几处**，别让它平均用力

### 6. 小的事控制方自己改，别再开一轮

复审提了三处**会误导的说明文字与错误信息**（两行注释 + 一句错误消息）。这类属「**做工**」不属「**结构**」，控制方直接改掉 + 跑一遍验证 + 提交，比再派一个子代理快得多，也不损失什么。

**判据**：改动**不碰行为**、**不能出错**（如注释措辞）、**验证一条命令就能完成** → 自己做。

### 7. 凡是「查询」，都要让「现在」可注入——判据不是它在哪个包

计划 3 收口后发现的缺陷。三个能力函数（`holdings` / `industryAllocation` / `financials`）用挂钟给「查哪一年」补默认值：

```ts
const year = opts.year ?? new Date().getFullYear()
```

**为什么它是 bug：**

1. **「现在」不是这个函数的输入。** 它们是**查询**：输入是「要哪一期」。用挂钟补默认值，等于把环境依赖塞进本该由调用方决定的参数里。查历史时，「现在」无关
2. **只在跨年那一刻发作，所以验收永远碰不到。** 开发、测试、验收都在同一年 → 那条分支走不到。**这类 bug 的特征是「写的时候是对的」**
3. **规矩的边界画错了层。** `CONSTRAINTS` 只写了「`core` 不读时间」。可「不读时钟」的理由——**可测、可复现、结果只取决于输入**——对**任何查询**都成立。当时把这条写在 `core` 的约束底下，能力层就漏了
4. **它长得不像 bug。** `new Date().getFullYear()` 是一行「看起来正常的防御性默认值」，没有异味，审查不会停下来看

**最要命的是第五点：有第二个 bug 把它盖住了。**
`selectPeriod` 在指定月份找不到时**静默回退到最新一期**。于是「查错了年份」不报错，只是返回**另一期**的数据。两个 bug 叠起来：要 2025 年 6 月的持仓 → 查了 2026 → 没有 → 悄悄给 2026Q3，`dataAsOf` 写着 2026-09-30、`loss: null`。**要的是一样、拿到的另一样、没有任何信号。**

**照做：**

- **凡是结果不该随挂钟变的函数，一律让「现在」可注入**（照 `fetchWithFallback` 的 `spec.now`）。**这不是为了「可配置」，是为了可验证**
- **默认值要配一条把时间钉死的测试**（如 `now` 固定为年初），否则跨年行为等于没验过
- **验收「查最新」这类能力时，要问「年初会怎样」**——年初是这类 bug 唯一的窗口
- **一个默认值出问题时，先找有没有第二个 bug 把症状抹平了。** 静默回退（找不到就用别的）和错误默认值叠在一起，会伪装成正常结果

### 8. 什么值得深究，什么不值得

| 深究 | 一句话放过 |
|---|---|
| 会**静默出错值**的（缓存键、降级口径、软失败） | 注释措辞 |
| 会**污染账本**的（分红/折算的字段语义） | 断言合并方式 |
| 会**让用户误判**的（`loss` 说没说清、错误信息是否误导） | 命名偏好 |
| 下游有任务依赖的 | 计划文档里的计数漂移 |

## 并行 vs 串行：多个代理共用一个工作区会互相污染

计划 2 期间用四个代理并行改同一批目录，**三次**出事：

| 形态 | 发生了什么 |
|---|---|
| `--amend` 卷走 | A 代理 `--amend` 时把 B 已经暂存到索引的改动一起提交，提交信息与内容不符 |
| 抢先提交 | A `git add` 后、`commit` 前，B 先提交了，把 A 的暂存内容一起带走 |
| 互相抵消 | 上面的后果被发现后，一方 `reset --soft` 撤下重提，结果**两头都没了**（XIRR 的 181 行一度只在工作区） |

**判据：改同一批文件、或都要改共享文件（`index.ts`、类型定义），就不能并行。**

**照做：**

- **并行只在「文件完全不相交」时用。** 例如计划 3 里「加 CI」和「改计划文档」可以并行（`.github/` vs `docs/`）；计划 2 里「五个 `risk/*.ts`」不行（都要改 `index.ts`）
- **要动公共签名/类型的任务一律串行。** 品牌类型那次如果并行，五处 `AdjustedNav` 的改法会各写各的
- **改同一文件时，简报里写死「只追加自己那几行」「`index.lock` 冲突等两秒重试」** —— 但这只降低概率，不消除
- **代理报告里出现「提交信息与实际内容不符」「我的改动被某某提交带走了」，就该停下来串行**，别当成一次性事故

## 设计阶段没问的三个问题，事后要各花一轮返修

计划 1–4 的五条 Critical 里，**有四条的根因在计划的语义定义**，不在实现：

| 缺陷 | 该在设计时问的问题 |
|---|---|
| `fee` 被当买入成本 | **这个字段缺失/不适用时，语义是什么？**（`fee` 类型里没有「属于哪笔交易」，只能猜） |
| 风险指标吃未复权净值 | **这个类型的值是什么口径？**（`NavConfirmed` 没说未复权还是复权） |
| 推导忽略 `ledgerId` | **这个函数的输入域是什么？**（§7.2 说挂在账本下，推导层却不认账本） |
| `navHistory` 截断在 4000 条 | **这个上限对真实数据够不够？**（20 年基金约 5900 条，写 `MAX_PAGES=200` 时没人算过） |

**照做：每份计划里，每个进入 `core` 或跨层的类型，加一行回答这三个问题：**

1. **口径**：什么单位 / 是否已调整 / 与哪个字段对应
2. **缺失**：`null` 还是 0？代表什么？
3. **域**：它属于哪个账本 / 哪个基金 / 哪一笔？

**成本对比**：一句话的问答 vs 一轮返修（约 2–3 个任务的工作量）。计划 1–4 累计多花了约 30%。
