# 账本与持久化设计（计划 4）

> 2026-11-19 · 依据 `docs/CONSTRAINTS/` 的 §一（技术栈与扩展缝）、§二（分层规矩）、§六（账务规矩）、§七（账本概念）、§九（流程与写法总原则）
> 本文件是**设计**；任务拆分见随后的计划。

## 一、这层存在的理由

不是「把数据存起来」。是：**当账对不平时，它拦住你，而不是悄悄改账。**

`CONSTRAINTS §6` 里那句「一致性检查，不做自动修正……绝不悄悄改账」是这一层的全部意义。存流水、算持仓都是手段；**能不能在份额对不上时停下来问一句**，才是它和「一个 Excel 表」的区别。

## 二、目标

- **账本（多账本）从第一天就有** —— §7.2 说这是唯一一个「后补很痛」的决定，往所有表加字段并回填代价很大
- **存流水，不存持仓状态**；持仓、成本、份额一律由流水推导
- 流水覆盖：申购 / 赎回 / **现金分红** / **红利再投** / **份额折算** —— 前三者是不同事件，分开记。
  **费用不单列**，并进它所属于的那笔买卖（见 §七）
- 从流水推导持仓（纯函数）
- **一致性检查**：用「上期确认份额 + 期间流水」推算应有份额，与用户录入比对；不一致就拦住并要求确认
- SQLite（`node:sqlite`）+ Drizzle（`sqlite-proxy` 适配器，§一 已实测跑通）
- 把计划 3 留的那道缝落地：`CacheStore` 的 **SQLite 实现**（现在只有内存实现）

## 三、非目标

- 界面、录入方式（计划 5 / 6）
- 估值、归因、预警（计划 5）
- **从数据源拉分红/折算并生成待确认事件**（计划 5）——但 schema **预留状态字段**，见 §七
- HTTP 服务（计划 5）。本计划只建 `apps/server/src/` 下的 db 与 repository，没有路由

## 四、反目标

| | 表现 | 必须怎样 |
|---|---|---|
| **静默改账** | 份额对不上，系统自己「修正」了 | 拦住并要求确认，**绝不自动修正** |
| 用估算值记账 | 盘中估值被记成一笔真实份额变动 | 记账只接受确认净值（三种价格类型已在编译期隔离） |
| 假装有盈亏 | 成本价查不到却显示收益 | §6：成本价可缺，缺了就**只做风险跟踪、不显示个人盈亏**，并标注原因 |
| 单账本写死 | 表结构里没有「账本」这一层 | 所有表都挂在账本下 |

## 五、已定的约束（不再讨论）

- **数据挂在「账本」下，不是挂在「用户」下**（§7.2）
- **存流水不存状态**；持仓由流水推导（§6）
- **必须支持 `split`（份额折算）**，否则账永远对不平（§6）
- **现金分红与红利再投是两种事件**（§6）
- **一致性检查不做自动修正**（§6）
- **成本价可缺**（§6）
- **收益两个数分开放**：资金加权（XIRR，「这笔钱赚多少」）与时间加权（TWR，「经理行不行」）（§6）——两者都已在 `packages/core` 实现
- Drizzle + `node:sqlite`，`sqlite-proxy` 适配器（§一）

## 六、方案（已选）

| 部分 | 放哪 | 为什么 |
|---|---|---|
| **推导**（流水 → 持仓/成本/份额、一致性检查） | `packages/core/src/ledger/` | 纯计算。放这里才能「数进数出」地测——放 `apps/server` 就得起一个 SQLite 才能验一次份额折算。**§二 规则 1「core 才算数」** |
| **持久化**（SQLite 读写、Drizzle、适配器） | `apps/server/src/` | 有 IO。§二 的分层里 Repository 就在这一侧 |
| **CacheStore 的 SQLite 实现** | `apps/server/src/` | 同上；它 `implements` 计划 3 定义的接口 |

**考虑过、否掉的：**
- 新造 `packages/ledger` —— 撞 §二 规则 1（纯计算与 IO 混在一包），且违反目录约定（只列了 4 个包）
- 全放 `apps/server` —— 推导逻辑变得不可单测，而它恰恰是最该手算验证的部分
- 不用 Drizzle 直接用 `node:sqlite` —— 更省事，但 §一 已把 Drizzle 定为三道扩展缝之一（将来换 Postgres 只改 dialect）；使用者选按 §一

## 七、数据模型

三张表。**所有业务表都带 `ledgerId`。**

```
ledger          账本        id / name / currency / createdAt
transaction     流水        id / ledgerId / fundCode / date / kind
                            / sharesDelta / splitRatio / amount / status
                            / source / note / createdAt
reconcile       对账记录    id / ledgerId / fundCode / asOf / claimedShares
                            / derivedShares / matched / note / createdAt
```

**份额为什么是两列而不是一列**：份额折算存的是**比例**（`1:0.3709`），其余事件存的是**增减量**——两者量纲不同。合成一列（「这列按 kind 分支解释」）会让实现者把折算存成增减量或折算后总份额，派生份额与成本立刻全错。故 `sharesDelta` 与 `splitRatio` 各自单一含义，互斥使用。

**`transaction.kind` 的取值**（`§6` 要求分红与再投分开）：

| kind | `sharesDelta` | `splitRatio` | `amount` | 必填校验 | 说明 |
|---|---|---|---|---|---|---|
| `subscribe` 申购 | **必填** + | — | − | `sharesDelta` | 买入。`amount` = 买入金额**含申购费** |
| `redeem` 赎回 | **必填** − | — | + | `sharesDelta` | 卖出。`amount` = **已扣赎回费后的到账额** |
| `dividend_cash` 现金分红 | 0 | — | + | — | 份额不变、现金离开基金 |
| `dividend_reinvest` 红利再投 | **必填** + | — | 0 | `sharesDelta` | 份额增加，无外部现金流；`amount` 为**再投金额**（属收益不属现金流），推导时**按两步展开**，见 §八 |
| `split` 份额折算 | — | **必填** 比例（如 `0.37094933`） | 0 | `splitRatio` | **用户无操作份额也会变**（`510300` 实测） |

**没有独立的 `fee` 类型（2026-11-19 修订）。** 原设计有 `fee` 一类，写「计入**对应**买卖的成本」——但类型里**没有「这笔费属于哪笔交易」的字段**，实现者拿到一条孤立的费用记录只能猜，于是把赎回费摊进了**剩余持仓**的成本：单位成本虚高、已实现收益虚增，两个数都「看着合理」。

**费用一律并进它所属于的那笔交易**：申购费进 `subscribe.amount`，赎回费从 `redeem.amount` 里扣。这样**结构上不可能记错**——费用天然属于那笔交易，没有猜的余地。
看不到费用明细是代价，但个人账本用不上。（另一方案是加 `refId` 指向所属交易，更精确，但多一个字段、且记错时**仍会**静默算错，故不取。）

**必填校验**：上表「必填校验」一列里的字段缺失时**抛 `TypeError`**，不按 `?? 0` 静默当零——`redeem` 缺份额会变成「赎回 0 份、整笔回款全计入已实现收益」，凭空虚增收益。

**`transaction.status`**：

- `confirmed` 已确认 —— **计划 4 只实现这条路径**
- `pending` 待确认 —— schema 里预留；计划 5 从数据源拉到分红/折算时生成，**用户确认后才变 `confirmed`**

**为什么状态字段现在就要有**：`§6` 说「能取到数据 ≠ 能自动记账」，而现金分红与红利再投自动判错会让账静默出错。计划 5 接数据源时若发现没有地方放「待确认」，就得加字段 + 回填——正是 §7.2 说的那种「后补很痛」。

## 八、推导（`core/ledger/`，纯函数）

**两个入口，签名不同（不要合成一个）：**

- `derivePosition(transactions, asOf)` —— 从**全部已确认流水**推某只基金在某日的份额、成本、已实现收益
- `deltaBetween(transactions, from, to)` —— 期间流水对份额的净影响，供对账用

**两者都只吃 `status === 'confirmed'` 的流水。** 这条是**契约的一部分**：计划 5 会塞进 `pending` 待确认流水，若不按状态过滤，它们会被**静默算进持仓**。

### 持仓份额
按日期累计各 kind 对份额的影响；`split` 按 `splitRatio` 乘。

### 成本：移动加权平均 + 已实现收益单列

| 事件 | 份额 | 总成本 | 已实现收益 |
|---|---|---|---|
| 申购 | + | + 买入金额（含申购费） | — |
| 赎回 | − | **按比例结转**（单位成本不变） | + (卖出回款 − 结转成本)；赎回费从回款里扣 |
| 现金分红 | 0 | **不变** | **+ 分红金额** |
| 红利再投 | + | **+ 再投金额** | 见下 |
| 份额折算 | 按 `splitRatio` 乘 | **不变** | — |

费用不单列：申购费含在申购金额里、赎回费已从回款里扣（见 §七）。

**红利再投按两步展开**：先是一笔现金分红（记已实现收益），紧接着按再投净值买入（成本增加、份额增加）。这两步正是 `§6` 要求「现金分红与红利再投分开记」的原因——**它们对成本与份额的影响完全不同**。

**为什么选这个口径**（使用者 2026-11-19 定）：单位成本是稳定的买入均价，**好核对**；已实现收益与浮动盈亏分开，符合本项目一贯的「分开放」口径（`§6` 的 XIRR / TWR 也是这么分的）。
另一种「摊薄成本」（成本 = 累计买入 − 累计卖出回款 − 现金分红，再除当前份额）数字上会跟天天基金 / 支付宝一致，但**成本价会退化成没有独立含义的派生量**，赎回后跟平台对不上时不好判断谁错。

### 成本价缺失
流水中若没有买入记录（例如只从某个时点开始记），成本与成本价一律标为**未知**，不编一个数。`§6`：此时只做风险跟踪、**不显示个人盈亏**，界面标注原因。

### 收益
**计划 4 不调 `xirr` / `timeWeightedReturn`。** 它只产出 `CashFlow` 序列（纯函数、可测）。

理由：XIRR 需要「当前市值」当最后一笔现金流，TWR 需要估值点序列——**两者都是估值，属计划 5**。在那里才有市值，也才该调这两个函数。本层连「现在净值是多少」都不知道，调了只能编。

## 九、一致性检查（`core/ledger/`，纯函数）

输入：某基金、截止日、**用户声称的实际份额**。

1. **从全部已确认流水重推**该基金在截止日的应有份额
2. 与用户声称的份额比（**用 `approxEqual`，不用 `===`**，§8.1）
3. 一致 → 记一条 `matched: true`
4. **不一致 → 记一条 `matched: false`**，把差异如实报出来（差多少、**上次对得上的日期**），要求用户确认。**绝不改流水**

**不做「最早从哪一天开始对不上」的推算（2026-11-19 修订）。** 原设计写了这一项，但它是**推算**，不是事实：要逐日回推比对才能得出，代价不小，而算出来的结果仍然可能指错（同日多笔顺序不保证、补录的流水没有可观测的边界）。字段因此命名为 **`lastMatchedOn`**（上次对得上的日期），**不叫 `sinceDate`**——名字不能许诺它算不出来的东西。真要查，翻流水比看一个推算日期可靠。

**为什么是全量重推，而不是「上期确认份额 + 期间流水」的增量**：增量模型有个静默漏洞——用户事后补录一笔**早于上次对账日**的流水时，那笔既不在上期确认份额里、又落在本期窗口之外，**会被默默漏掉**。个人账本的流水量很小（几千条），全量重推是毫秒级，用增量换不来任何东西，只换来个静默漏洞。

**不做**：自动插一条「调整」流水把账抹平。

## 十一、这是谁的决定

| 决定 | 谁定的 |
|---|---|
| schema 预留「待确认」状态，但计划 4 只做已确认路径 | 使用者 |
| 用 Drizzle（而非直接用 `node:sqlite`） | 使用者 |
| **成本口径：移动加权平均 + 已实现收益单列** | 使用者（2026-11-19） |
| 推导进 `core/ledger`、持久化进 `apps/server` | 控制方（§二 规则 1 推出来的） |
| 计划 4 不做界面与录入方式 | 控制方 |
| 多账本从第一天就有 | 约束 §7.2（本来就是「现在就要做」） |
| 对账用**全量重推**，不用增量水位线 | 控制方（增量有「补录早于上次对账日会静默漏掉」的漏洞） |
| 份额拆成 `sharesDelta` 与 `splitRatio` **两列** | 控制方（一列两种量纲会把人往错里带） |
| 推导**必须过滤 `status !== 'confirmed'`** | 控制方（否则计划 5 的待确认流水会被静默算进持仓） |
| 计划 4 **不调** `xirr` / `timeWeightedReturn` | 控制方（两者都要市值，那是计划 5 的估值） |
