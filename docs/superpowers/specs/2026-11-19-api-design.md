# 服务端 API 设计（计划 5 · MVP 收缩版）

> 2026-11-19 · 依据 `docs/CONSTRAINTS/`（§二分层、§4 硬规则、§6 账务、§9.3 运行形态、§9.5 最简优先）、`docs/superpowers/specs/2026-11-19-ledger-design.md`、`docs/ROUTE.md`、`docs/LESSONS.md`
> 本文件是**设计**；任务拆分见随后的计划。

## 一、这一层存在的理由

不是「把 JSON 吐给前端」。是：**让前端不可能拿到一个没标注口径的数字。**

前端不做计算、不做单位换算、不知道净值有两种口径。它拿到的每个数字都自带出处与时点；拿不到时明确拿到「算不出来」，而不是一个 `null` 被当成 0。

## 二、目标

- `apps/server` 长出 **Service 层**与**只读 + 录入路由**
- 把已有的 `Repository` / `FundDataSource` / `core` 串起来，**Service 不写算式**（§二 规则 1）
- 能查到：账本、持仓、搜基金（按类型筛选）、基金档案、单基金净值走势与风险、组合风险、对账结果
- 能新建账本（否则首次运行没有账本可用）
- 能录入：一笔流水
- **每个数字都带口径**：`dataAsOf` / `stale` / `loss`

## 三、非目标（MVP 砍掉，明确不做）

| 不做 | 为什么 |
|---|---|
| **持仓穿透估算**（新前十权重 + 旧全量尾部） | 需多基金 × 多交易日的误差分布统计才能定阈值；AGENTS.md 明说单日观测「不是精度结论」。**这是独立的统计工作，不是开发任务** |
| **归因式预警** | 依赖穿透估算。且反目标 A2：不归因的预警两周内被全部屏蔽，做浅等于没做 |
| 定时任务 CLI | 手动触发足够验证 MVP |
| 前端 | 计划 6 |
| 分红自动入账 | §6：能取到 ≠ 能自动记账，仍须用户确认 |
| TWR（时间加权） | 需要估值点序列，而账本只有流水；衔接设计未做。**只做 XIRR** |

## 四、两条口径决定（这一层的核心）

### 4.1 净值有两个口径，不能混用

| 用途 | 用哪个 | 为什么 |
|---|---|---|
| 风险指标（波动、回撤、相关性） | **复权净值**（`toAdjustedSeries` 产出，品牌类型 `AdjustedNav`） | 未复权净值在分红除息日机械下跌，会造出假回撤 |
| XIRR 的期末市值 | **未复权单位净值 × 份额** | 那才是真能赎回拿到的钱 |
| 净值走势图 | **两个都给** | 用户看「价格」和看「我的实际回报」是两个问题 |

**用反了的后果**：XIRR 若用复权净值当期末市值，而分红又作为现金流单独计入 → **同一笔分红算两次**，收益率虚高。

### 4.2 `toAdjustedSeries` 必须在这一层接上

`toAdjustedSeries` 目前**没有任何调用点**。品牌类型只在 `core` 内部生效，API 若直接把 `navHistory` 的原始 `rows.map(r => r.nav)` 吐给前端，前端再调风险接口就会编译失败——但那只是把错误推到了前端。

**本层必须在服务端完成复权**，API 只输出 `AdjustedNav` 或明确标注为未复权的原始净值。

## 五、分层与装配

```
Route (Fastify)     校验入参、调 Service、返回
   ↓
Service             编排：取数（DataSource）→ 算（core）→ 存（Repository）
   ↓
   ├── Repository   账本/流水/对账/缓存
   ├── DataSource   FundDataSource（20 端点）
   └── core         纯计算
```

**Service 不写算式**——§二 规则 1。`derivePosition`、`xirr`、`maxDrawdown` 一律从 `@fundmanager/core` 调。

**装配点只有一处**：`apps/server/src/app.ts` 组装 `db → repositories → FundDataSource → services → routes`。

## 六、路由

**按资源归属划分，不把所有东西硬挂在账本下。**

判据：这个数据是**因为我持有才存在**，还是**市场本来就有**？

- 持仓、盈亏、组合风险、对账、流水 → **因为持有才存在** → 挂 `/api/ledgers/:ledgerId`
- 净值、基金档案、单基金风险 → **市场本来就有** → 挂 `/api/funds`
- 「这只基金我赚了多少」（XIRR）→ 没有你的流水就没有这个数 → 挂账本

（这是 2026-11-20 的修订。原设计把所有业务路由都挂 `ledgerId`，导致「用账本 1 去查全市场净值」这种语义不通的路径。净值与账本无关，账本 ID 是被迫带上的。）

### 账本内的数据

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ledgers` | 账本列表 |
| POST | `/api/ledgers` | **新建账本**（首次运行必须能建，否则后面全用不了） |
| GET | `/api/ledgers/:ledgerId/positions` | 该账本全部持仓 |
| GET | `/api/ledgers/:ledgerId/positions/:fundCode` | 单只基金持仓详情 |
| GET | `/api/ledgers/:ledgerId/funds/:fundCode/return` | XIRR（**未复权净值 × 份额**） |
| GET | `/api/ledgers/:ledgerId/portfolio/risk` | 组合风险：相关性矩阵 + 组合回撤 |
| POST | `/api/ledgers/:ledgerId/transactions` | 录入一笔流水 |
| POST | `/api/ledgers/:ledgerId/reconcile` | 对账（用户声称份额 → 结果） |
| GET | `/api/ledgers/:ledgerId/reconcile/last` | 上次对得上日期 |

### 市场数据（与账本无关）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/funds?q=&category=&limit=` | **搜基金**，按代码/名称/拼音匹配；**可按类型筛选** |
| GET | `/api/funds/categories` | **可选类型清单**（从数据里聚合出的实际取值，不另外发明分类体系） |
| GET | `/api/funds/:fundCode` | 基金档案（名称/类型/业绩比较基准/跟踪标的） |
| GET | `/api/funds/:fundCode/nav` | 净值历史，**同时返回未复权与复权** |
| GET | `/api/funds/:fundCode/risk` | 单基金风险（这只基金自身的波动/回撤特征，与持有无关） |

**搜索用数据源已有的 `FundCodeEntry`**（`code` / `name` / `abbrev` / `pinyin` / `category`），不新建分类体系：

- `q` 匹配代码、名称、拼音简写、拼音全拼 —— 四种都要，用户可能输 `011609`、`华夏`、`HXCZ` 或全拼
- `category` **精确匹配**数据源给的原始类型字符串（如 `混合型-灵活`），不做归一化——归一化会制造一个第二套分类，与数据源对不上
- `limit` 默认 50，上限 200：28,370 条不能一次吐完

## 七、返回信封

每个可能来自外部数据的数字都带出处。**这是本层唯一不能省的复杂度**：

```ts
type Sourced<T> = {
  value: T | null       // null = 算不出来，原因看 reason（§8.3：无解 → null，不是 0）
  reason: string | null // value 为 null 时的可读原因，如「成本未知」「净值不足两个观测」
  source: string        // 哪个端点给的
  dataAsOf: string      // 数据本身的时点：净值日 / 报告期
  capturedAt: string    // 抓取时刻
  stale: boolean        // 来自缓存降级
  loss: string | null   // 来自更弱的源，失去了什么
  provenance: readonly Sourced<unknown>[] // 派生值的各输入标注；直接来自外部数据时为空
}
```

**派生值（持仓、盈亏、风险指标）**：`dataAsOf` 取**最早**的输入时点（保守），各输入的标注放进 `provenance`。`stale` 取「任一输入 stale」；`loss` 取各输入的 loss 拼接（用 `；` 分隔，空则 null）。

**粒度**：**一个响应一个信封**；多行数据（持仓表、净值序列）改为**逐行带 `dataAsOf`**，不逐行套完整信封——4000 行的净值序列不可能每个数字带六个字段。

**哪些数字必须带口径**：凡是**依赖外部数据**的数（净值、持仓市值、盈亏、风险指标）。纯账本内生的（`shares`、`date`、`realizedGain`）**不必**——它们的可信度由账本本身保证，账本的正确性由对账守。

**算不出来的东西**：`value: null` + `reason`，**不是 0**。§8.3：无解 → `null`。

**复权序列可能失真**：`toAdjustedSeries` 在备源缺分红事件时，复权结果仍可能含假回撤（其 JSDoc 已写明）。这种情况下 `loss` 必须带出「复权时缺少分红数据」——否则风险数字会以 `stale: false` 的样子出现，正是反目标 A3。

## 八、错误翻译（计划 4 遗留的必做项）

`core` 抛的 `TypeError` 是给开发者看的，**不能原样吐给用户**：

| `core` 抛的 | 用户在界面上该看到 |
|---|---|
| 超赎：「赎回 120 份但账面只有 100 份」 | 「这笔赎回超过了账面份额，请先补录买入」 |
| 同日缺 `sequence` | 「同一天有多笔流水，需要指定先后顺序」 |
| 同日 `sequence` 重复 | 「同一天的顺序号重复了」 |
| 缺必填字段 | 「这笔记账缺少份额」 |

**映射表集中在一处**（`apps/server/src/errors.ts`），不要在每条路由里各写一遍。

## 九、缓存与降级

复用 `packages/datasource` 的 `FundDataSource` 与 `CacheStore`（计划 4 已有 SQLite 实现）。

**`stale` 要穿透到 API**：数据层返回 `stale: true` 时，路由必须原样带出，不能因为「反正有值」就当成新鲜数据。**这是反目标 A3 在本层的落点。**

## 十、运行形态（§9.3 已定，这里落地）

前后端分开跑。开发时前端走 Vite dev server、后端单独启动。**三项待定，本计划定**：

- **API 端口**：可配，默认 `5178`（避开 Vite 的 5173）
- **前端如何得知 API 地址**：`VITE_API_BASE` 环境变量，默认 `http://localhost:5178`
- **CORS**：开发时允许 `http://localhost:5173`；生产由前端静态服务同源代理，不开宽 CORS

## 十一、测试

| 测什么 | 怎么测 |
|---|---|
| Service 编排 | 用**假 Repository + 假 DataSource**，断言它调了哪个 core 函数、传入的序列是不是复权的 |
| 路由 | Fastify 的 `inject`，不起真端口。断言：信封字段齐全、错误被翻译成可读信息、`stale` 透传 |
| 复权接线 | **一条端到端用例**：喂未复权净值 + 分红事件，断言风险接口返回的回撤**不含假回撤** |

## 十三、API 手册（`docs/api.md`）

**要一份给人查的手册，不是给编译器看的类型。** 使用者 2026-11-19 明确要求。

**放在最后做**：所有路由跑通、测试全绿之后再写。接口没定稿就写手册，改一次废一次。

### 必须包含

| 章节 | 内容 |
|---|---|
| 总则 | base URL、端口、CORS、`ledgerId` 的含义（是「一本账」，不是「一个用户」） |
| 信封说明 | `Sourced<T>` 七个字段逐个解释，尤其 `stale` / `loss` / `reason` 为什么存在 |
| **口径警告** | 净值有两种口径，哪个端点是哪个；用反了会怎样（分红重复计入） |
| 每个端点 | 方法、路径、参数、请求体、**真实示例响应**、可能的错误 |
| 错误码表 | `core` 的 `TypeError` → HTTP 状态 + 可读信息 |
| 常见坑 | 「成本未知时 `value: null` 而非 0」「`provenance` 是什么」「`loss` 非 null 意味着什么」 |

### 铁律

**示例响应必须是真跑出来的，不能手写。**

手编的示例有两个问题：一是**最容易过期**（改了实现没人改示例），二是**最容易被复制**（前端照着示例写解析，示例错了就一起错）。

做法：写完路由后用 `curl` 打真实服务，把响应原文贴进手册；手册里注明「抓取于 YYYY-MM-DD，样本账本 N 笔流水」。

### 不做的

- 不写 OpenAPI/Swagger 规格：一个人用、一个消费者，收益撑不起维护成本（§9.5）
- 不建文档站：Markdown 一份够了

## 十四、留给实现者的

- 每个字段的具体 JSON 形状（本文件只定信封与语义）
- Service 之间是否复用某个共享的「取净值并复权」小函数
- 分页（持仓通常几十条，可能不需要）
- 录入流水的校验细节（`sequence` 由前端给还是服务端自动分配）
